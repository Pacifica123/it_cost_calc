# Исследование: AHP-анализ конфигураций

## Зачем нужен этот модуль

AHP-модуль предназначен для выбора оптимальной конфигурации оборудования из множества альтернатив, когда решение нельзя свести только к одной цифре стоимости.

Важная идея здесь такая:
- сначала отсеиваются варианты, которые не проходят по жёстким ограничениям;
- затем оставшиеся конфигурации сравниваются по мягким критериям;
- доменный AHP-pipeline поддерживает экспертные матрицы критериев;
- текущий scoped Qt-сценарий использует профильные веса критериев и score-derived отношения альтернатив, поэтому его нельзя описывать как сбор экспертных попарных оценок альтернатив.

## Что подаётся на вход

Для общего доменного AHP-pipeline на вход подаются:

- список конфигураций;
- список мягких критериев;
- матрицы попарных сравнений критериев от экспертов;
- словарь жёстких ограничений.

В текущем scoped Qt-потоке критерии и их веса берутся из `AnalysisScopeProfile`, а локальные pairwise-матрицы альтернатив строятся автоматически из utility-score `1..5`. Это AHP-based score-derived ранжирование, а не интерфейс экспертного анкетирования альтернатив.

В коде это сосредоточено в:
- `src/domain/decision/ahp/configuration_selector.py`
- `src/domain/decision/ahp/pipeline.py`

## Что происходит внутри

1. Каждая конфигурация агрегируется в набор сводных показателей.
2. Применяются жёсткие ограничения.
3. Для критериев агрегируются экспертные оценки.
4. Для каждой группы альтернатив строятся матрицы попарных сравнений.
5. Вычисляются приоритеты и итоговые веса.
6. Строится ranking альтернатив и выбирается победитель.

## Что получается на выходе

На выходе формируется отчёт, в котором есть:
- список прошедших альтернатив;
- детали отфильтрованных конфигураций;
- веса критериев;
- локальные веса альтернатив по каждому критерию;
- итоговое ранжирование;
- выбранная лучшая конфигурация.

## Связь с дипломными материалами

AHP-направление связано с академическим сценарием выбора оптимальной конфигурации оборудования: постановкой задачи, иерархией критериев и применением метода анализа иерархий.

Тяжёлые исходные офисные файлы больше не хранятся в репозитории; переработанное описание этой связи фиксируется в текущем исследовательском документе и в `docs/thesis/project_academic_overview.docx`.

## Связь AHP с общей моделью после roadmap

После завершения roadmap AHP больше не следует понимать как изолированную вкладку с собственным набором конфигураций. Его роль — ранжировать общий пул `CandidateConfiguration`.

Практическая цепочка выглядит так:

```text
runtime/demo/GA alternatives → CandidateConfigurationService → candidate_configurations → AHP ranking → Hybrid/DecisionReport
```

Это означает:

- AHP работает с тем же общим пулом альтернатив, который формирует GA и затем используют Pareto, Hybrid и DecisionReport;
- различие ПО и ТО задаётся не вкладкой, а `AnalysisScopeProfile`;
- критерии и ограничения должны быть согласованы с профилем анализа;
- результат AHP становится отдельной частью `DecisionReport`, где рядом с ним показываются GA, Pareto, Hybrid, TCO и NPV.

Для дипломной защиты AHP удобно объяснять так: метод не генерирует инфраструктуру сам, а помогает выбрать лучшую альтернативу из уже сформированного и нормализованного пула. В текущем GUI веса критериев заданы профилем области, а сравнение альтернатив выводится из их количественных score; поэтому `CR` таких матриц не следует называть показателем согласованности экспертных мнений.
