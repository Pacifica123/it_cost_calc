# Граница между приложением и каталогом оборудования

## Базовый принцип

В проекте используется следующая модель:
- **основное приложение** отвечает за расчёты, анализ, сравнение конфигураций и формирование отчётов;
- **слой структурированных источников** получает XLSX/CSV/YML/XML и фиксирует provenance;
- **инструмент обновления каталога** сохраняет legacy/offline parser-сценарии и CLI-диагностику;
- **catalog staging** выступает проверяемой границей перед runtime-альтернативами оборудования.

Иными словами, GUI не должен зависеть от Playwright, anti-bot обхода и HTML-разбора витрин.
Основной сетевой путь GUI — получение структурированного feed-файла отдельным CLI-процессом,
после чего данные проходят обычный staging.

## Где проходит эта граница в репозитории

### Основное приложение
- `src/`

### Вспомогательный инструмент обновления каталога
- `tools/catalog_parser/`
- `scripts/update_equipment_catalog.py`

### Сырые и нормализованные данные
- `data/examples/parser/` — сохранённые примеры сырых снимков;
- `data/examples/catalog/` — пример нормализованного каталога;
- `data/generated/catalog/` — рабочий выход инструмента.

## Практический поток данных

1. пользователь выбирает локальный файл либо структурированный URL-источник;
2. URL-feed скачивается отдельным `feed-download` процессом вместе с `fetch_manifest.json`;
3. XLSX/CSV/YML/XML преобразуется в унифицированные staging-карточки;
4. `source`, `observed_at`, `price_kind` и `field_provenance` сохраняют происхождение значений;
5. staging показывает ошибки и предупреждения;
6. пользователь подтверждает нужные готовые устройства;
7. подтверждённые записи переносятся в `server`, `client` или `network` как исходные альтернативы ТО.

Legacy DNS/Yandex parser-режимы остаются в CLI для исследований и replay/offline диагностики,
но не являются основной пользовательской кнопкой каталога.

Подробный контракт описан в `catalog_staging_import.md`.

## Почему это лучше, чем встраивать парсер в GUI

Если парсер живёт внутри runtime приложения, то туда попадают:
- браузерные профили;
- сетевые сбои;
- нестабильные селекторы;
- антибот-ограничения;
- длинные операции и зависания UI.

Такая граница позволяет сохранить проект аккуратным:
- приложение остаётся настольным аналитическим инструментом;
- парсер остаётся отдельным техническим инструментом наполнения справочника.

Подробности нового feed-слоя: `catalog_feed_sources.md`.


## Независимые рыночные доказательства P4–P6

Поверх feeds/federation/Icecat каталог поддерживает три дополнительных канала:

- ЕИС/контрактные выгрузки как статистический `procurement_benchmark`, не как offer;
- коммерческие предложения как `commercial_quote` — наиболее доверенный ценовой тип;
- единичный browser capture из сохранённого HTML/JSON-LD без Playwright и без сетевого запроса приложения.

См. `catalog_evidence_p456.md`.
