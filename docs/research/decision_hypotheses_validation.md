# Проверка гипотез H1–H6 и риски для защиты

Документ фиксирует, что именно подтверждено математически, что воспроизведено текущим runtime проекта и какие формулировки безопасно использовать на защите. Для независимой повторной проверки добавлен `tools/validation/check_decision_hypotheses.py`.

## Итог по гипотезам

| Гипотеза | Статус | Граница утверждения |
|---|---|---|
| H1: геометрия `λ` | подтверждена | при фиксированном пуле и фиксированной нормировке каждая Hybrid-линия аффинна по `λ`; две неидентичные линии пересекаются не более одного раза |
| H2: сохранение доминирования | подтверждена | если нормированные GA и AHP у A не меньше, чем у B, выпуклая комбинация не может дать A меньший числовой Hybrid-score |
| H3: инвариантность масштаба | подтверждена | положительное аффинное преобразование одного raw-score сохраняет min-max значения только при том же непостоянном пуле |
| H4: инвариантность порядка при TCO-фильтре | опровергнута | перенормировка после удаления кандидата может изменить порядок оставшихся кандидатов; IIA не выполняется |
| H5: обратная NPV-задача | подтверждена | для постоянного годового эффекта `E*=O+I/A`; это порог безубыточности, а не прогноз эффекта |
| H6: score-derived AHP | подтверждена частично / clipping-гипотеза опровергнута | точная ratio-матрица воспроизводит исходные scores и имеет `CR=0`; нелинейный Saaty-cap может создать ненулевой CR |

Lean/kernel-проверка в проект не добавлялась. Эти статусы основаны на точной алгебре, рациональных контрпримерах, property-проверках и воспроизведении текущего Python runtime.

## Что реально опасно на защите

### 1. Высокий риск: назвать текущий scoped-AHP «экспертным попарным сравнением альтернатив»

Текущий Qt-сценарий `run_ahp_for_candidate_pool` не собирает экспертные pairwise judgments по альтернативам. Веса критериев берутся из `AnalysisScopeProfile.default_weights`, а значения кандидатов преобразуются в utility `1..5`, после чего pairwise-матрицы альтернатив строятся как отношения этих числовых scores.

Это отличается от классического учебного описания AHP, где эксперт непосредственно заполняет матрицы попарных сравнений. Безопасная формулировка:

> В текущем интерфейсе используется AHP-based score-derived ранжирование общего пула: веса критериев задаются профилем области, а локальные приоритеты альтернатив выводятся из нормированных количественных показателей. Отдельный доменный pipeline поддерживает экспертные матрицы критериев, но текущий scoped GUI не является формой экспертного анкетирования альтернатив.

Следствие: `CR` score-derived матрицы альтернатив нельзя выдавать за «согласованность мнений эксперта».

### 2. Высокий риск: смешать эффект TCO-фильтра с эффектом перенормировки

Старая sensitivity-логика после TCO-фильтра заново считала min-max по оставшемуся подмножеству. Поэтому удаление даже не победившего кандидата могло изменить шкалу и порядок оставшихся A/B. Это не чистый ответ на вопрос «что будет, если вариант станет недопустим по TCO».

Основная TCO-карта теперь использует **фиксированную baseline-нормировку** исходного экспортированного пула. Отдельно сохраняется `subset_renormalization_grid` как диагностический режим. Если две карты расходятся, отчёт предупреждает о normalization-context effect.

Безопасная формулировка:

> Основной TCO-сценарий меняет только допустимость внутри уже сформированного пула. Нормировочная база фиксируется по исходному пулу, поэтому эффект фильтра не смешивается с изменением шкалы. Перенормировка подмножества доступна только как диагностическая проверка контекстной чувствительности.

### 3. Средний риск: выдавать `λ`-сетку 0.05 за точные интервалы устойчивости

На фиксированном пуле

`H_i(λ) = A_i + λ(G_i-A_i)`.

Следовательно, точки возможной смены порядка вычисляются аналитически из попарных пересечений. Дискретная сетка нужна только для heatmap/визуализации, но не для расчёта точных границ и доли диапазона `λ`.

Sensitivity payload теперь содержит `exact_lambda.breakpoints`, `winner_intervals`, `winner_switch_points` и точную по длине диапазона `winner_shares`. Старый `lambda_sweep` сохранён как визуализационная сетка.

### 4. Средний риск: интерпретировать Saaty-cap как «улучшение согласованности»

Для score-derived ratio-матрицы `M_ij=s_i/s_j` выполняется `M s = n s`, поэтому при положительных scores приоритеты пропорциональны исходным scores, а `CI=CR=0`. Ограничение отдельных отношений до `1/9..9` является нелинейным преобразованием и может разрушить транзитивность отношений.

Контрольный пример `[1, 10, 100]` в текущем runtime даёт `CR≈0.4834773102` после clipping. В scoped GUI cap отключён. Для его текущей utility-шкалы `1..5` это также не меняет численный результат, потому что исходные отношения и так лежат внутри диапазона Саати.

### 5. Средний риск: придумать фактический экономический эффект в NPV

NPV корректно отвечает на вопрос только при заданном `annual_effect`. Если фактический эффект неизвестен, система не должна подставлять вымышленную выгоду. Теперь TCO→NPV дополнительно вычисляет `break_even_annual_effect`: минимальный постоянный годовой эффект, при котором NPV равен нулю для выбранной ставки и горизонта.

Безопасная формулировка:

> Это не прогноз выгоды, а порог: какой постоянный годовой эффект требуется, чтобы окупить заданные инвестиции и регулярные расходы при выбранной ставке дисконтирования.

### 6. Низкий риск: переобобщить H2/H3

H2 относится к **числовому Hybrid-score** при фиксированных нормированных доказательствах. H3 относится к фиксированному непостоянному пулу. Ни одна из них не доказывает независимость результата от состава множества кандидатов.

## Повторная проверка

Из корня проекта:

```bash
PYTHONPATH=src python tools/validation/check_decision_hypotheses.py
```

Скрипт использует `Fraction` для H1–H5 и текущие функции `domain.decision.ahp.math_utils` для runtime-воспроизведения H6. Ненулевой код возврата означает провал хотя бы одной проверки.
